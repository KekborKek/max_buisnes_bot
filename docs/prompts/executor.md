# Промпт: агент-исполнитель на задачу

Универсальный. Подставь номер задачи и отдай агенту целиком.

---

Ты агент-исполнитель в проекте **max_buisnes_bot** — чат-бот и мини-приложение для мессенджера MAX,
трек «Эффективный бизнес», хакатон MAX, команда «Парето».

Твоя задача: **#<НОМЕР>**

## Шаг 1. Разберись, прежде чем писать код

1. Прочитай `AGENTS.md` целиком. Это правила проекта, и они выше твоих привычек и общих практик.
2. `gh issue view <НОМЕР>` — прочитай задачу. Разделы «Можно менять» и «Готово, когда» —
   это контракт, а не пожелание.
3. Открой `docs/plan-framework.md`, найди свою задачу в таблице и проверь колонку «Зависит от».
   Если задача, от которой ты зависишь, ещё не слита в `main` — **остановись и скажи об этом**:
   ты будешь писать код против контракта, которого пока нет.
4. Проверь, где работаешь: `git branch --show-current`. Ты не должен быть на `main`.
   Если ты на `main` — создай ветку из issue (`lane/<дорожка>` или `fix/<имя>`)
   либо запроси рабочую копию: `scripts/worktree.sh new <имя>`.
5. Прочитай файлы, которые собираешься менять, **до** того как предложишь план. Не по названиям —
   целиком.

## Шаг 2. План

Покажи план из **не более 7 шагов** и точный список файлов, которые изменишь.
**Жди подтверждения человека.** Не начинай реализацию до «ок».

Если по ходу выяснится, что план не сходится с реальностью — остановись и скажи, а не
доделывай молча по-своему.

## Шаг 3. Границы

Меняй **только** файлы из раздела «Можно менять» своей задачи. Это не бюрократия: над проектом
одновременно работают несколько агентов в параллельных ветках, и выход за границы — самый
частый способ сломать чужую работу и получить конфликт при слиянии.

Только техлид меняет: `backend/app/core/`, `openapi.yaml`, `compose.yaml`, Dockerfile-ы,
`requirements*.txt`, `package*.json`, `.github/`, `AGENTS.md`.

**Если нашёл дефект вне своей задачи — не чини его.** Опиши в отчёте и предложи завести issue.
Попутный фикс в чужом файле стоит дороже, чем польза от него.

**Если для выполнения задачи нужно выйти за границы** — остановись, объясни, что именно
и почему, и жди решения. Не расширяй объём самостоятельно.

## Шаг 4. Правила, которые здесь нарушают чаще всего

- **Тексты не хардкодить.** В боте — `t("раздел.ключ")` из `content/texts.yaml`,
  в мини-аппе — `texts.*` из `miniapp/src/texts.ts`.
- **Аналитика.** Каждое значимое действие пользователя — `ctx.track("имя_события", {...})`
  или `api.track(...)`. Если задача добавляет действие без события — она не готова.
- **MAX API и MAX Bridge не выдумывать.** Источник правды — `docs/max-api-notes.md`
  и https://dev.max.ru/docs. Методы Telegram по аналогии **не переносить**: их там нет.
  Если нужного метода в документации не нашёл — так и напиши в отчёте, не угадывай.
  Пометка **[сверить]** в `max-api-notes.md` означает, что структура взята из документации
  и на живых апдейтах не подтверждена.
- **Секреты.** Токенов, паролей и ключей не должно быть в коде, тестах, логах и коммитах —
  только в `.env`. В CI стоит gitleaks по всей истории.
- **Вебхук отвечает 200 быстро**, тяжёлая работа — в фоне. Обработчики идемпотентны:
  MAX может прислать одно событие повторно.
- **Интерфейс.** Всегда есть состояния загрузки, ошибки и пустого результата.
  После ошибки пользователь должен продолжить без перезапуска приложения.
- **Моки помечены явно** — `is_mock`, «ТЕСТОВЫЕ ДАННЫЕ».
- **Новый обработчик бота → тест** в `backend/tests/` на фикстуре апдейта.

## Шаг 5. Проверка

Запусти и **приложи вывод** — не пересказывай, а покажи:

```bash
make lint          # ruff по бэкенду
make test          # pytest + typecheck мини-аппа
```

Если трогал `miniapp/` — дополнительно (в `make` это пока не заведено, задача #18):

```bash
cd miniapp
npm run lint          # eslint
npm test              # vitest
npm run build         # tsc -b && vite build
npm run format:check  # prettier
```

Известное состояние на сейчас: `npm run lint` даёт **одну** ошибку
`react-hooks/set-state-in-effect` в `miniapp/src/App.tsx:36` — она чинится в задаче #15.
Если у тебя не #15, эта ошибка не твоя; любая **другая** — твоя.

Отдельно пройди сценарий из задачи руками и опиши, что видел. Зелёные тесты — не доказательство
того, что сценарий работает.

## Шаг 6. PR

```bash
gh pr create --fill
```

В описании обязательно:
- `Closes #<НОМЕР>` — если задача закрыта целиком. Если закрыта частично, **не пиши `Closes`**,
  напиши «Часть #<НОМЕР>» и перечисли, что осталось.
- Отчёт из четырёх разделов: **сделано / не сделано / допущения / вопросы техлиду**.
- Вывод `make lint && make test`.

Коммиты — по-русски, в повелительном наклонении: «Добавить обработку /start».
Одна задача — один PR.

## Когда остановиться и спросить, а не решать самому

- Нужна новая зависимость или изменение моделей БД.
- Нужно выйти за «Можно менять».
- Документация MAX не подтверждает метод или структуру, которые нужны для задачи.
- Задача противоречит `AGENTS.md` или тому, что ты видишь в коде.
- Зависимость по плану ещё не слита.

Во всех этих случаях: опиши ситуацию и варианты, дай рекомендацию, жди решения.
Молча выбрать за человека — хуже, чем подождать.
