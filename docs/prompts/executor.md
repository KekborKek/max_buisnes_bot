# Промпт: агент-исполнитель на задачу

Универсальный. Подставь номер issue и код задачи из `docs/spec/plan.md` (T0, T5a, T11…) и отдай агенту целиком.

---

Ты агент-исполнитель в проекте **max_buisnes_bot** — «Календарь обязательств ИП»: чат-бот и мини-приложение
для мессенджера MAX, трек «Эффективный бизнес», хакатон MAX, команда «Максимы на парковке».

Твоя задача: **#<НОМЕР> (<КОД ЗАДАЧИ>)**

## Шаг 1. Разберись, прежде чем писать код

1. Прочитай `AGENTS.md` целиком. Это правила проекта, и они выше твоих привычек и общих практик.
2. `gh issue view <НОМЕР>` — прочитай задачу. Разделы «Можно менять» и «Готово, когда» —
   это контракт, а не пожелание.
3. Прочитай `docs/spec/README.md` и выполни порядок чтения оттуда: `product.md` целиком,
   `decisions.md` целиком, файлы под задачу (`data-model.md`, `reminders.md`, `docs/screens/NN-*.md`).
   Решения D1–D22 не переоткрывай.
4. Найди свою задачу в `docs/spec/plan.md` и проверь колонку «Зависит от».
   Если задача, от которой ты зависишь, ещё не слита в `main` — **остановись и скажи об этом**:
   ты будешь писать код против контракта, которого пока нет. Исключение прописано в самом плане
   (например, мини-апп на моках не ждёт API).
5. Проверь, где работаешь: `git branch --show-current`. Ты не должен быть на `main`.
   Если ты на `main` — создай ветку `feat/<код-задачи>-<кратко>` (например `feat/t5a-onboarding`).
6. Прочитай файлы, которые собираешься менять, **до** того как предложишь план. Не по названиям —
   целиком.

## Журнал передачи — ведётся всю задачу

Сессия может оборваться в любой момент (лимит запросов API), и заранее этого не видно. Чтобы
следующий агент не перечитывал всё заново, веди короткий журнал в
`<scratchpad>/handoff/<код-задачи>.md`
(не в репозитории). Обновляй его **после согласования плана и после каждого завершённого шага**,
перезаписывая целиком, не больше 40 строк:

- задача, ветка, worktree;
- согласованный план и решения планировщика (дословно, коротко);
- что сделано (файлы) и что осталось;
- неочевидное, что выяснил в коде и документации (чтобы не искать снова);
- состояние проверок (что зелёное, что красное и почему).

Если тебя запустили продолжить чужую задачу — **сначала прочитай журнал** и `git diff`, и только
потом открывай файлы, которых в журнале не хватает.

## Шаг 2. План

Покажи план из **не более 7 шагов**, точный список файлов, которые создашь и изменишь, и какие тесты
напишешь. **Закончи ход и жди подтверждения** (человека или планировщика). Не начинай реализацию до «ок».

Если по ходу выяснится, что план не сходится с реальностью — остановись и скажи, а не
доделывай молча по-своему.

## Шаг 3. Границы

Меняй **только** файлы из раздела «Можно менять» своей задачи. Над проектом одновременно работают
несколько агентов в параллельных ветках, и выход за границы — самый частый способ сломать чужую работу
и получить конфликт при слиянии.

Только техлид (или задача T0 по его поручению) меняет: `backend/app/core/`, `backend/app/main.py`,
`openapi.yaml`, `compose.yaml`, Dockerfile-ы, `requirements*.txt`, `package*.json`, `.github/`, `AGENTS.md`.

**Нашёл дефект вне своей задачи — не чини его.** Опиши в отчёте и предложи завести issue.

**Нужно выйти за границы** — остановись, объясни, что именно и почему, и жди решения.

## Шаг 4. Правила спецификации

- **Одна задача = свои экраны.** Соседний экран «заодно» не делай, даже если он в двух строках.
- **Тексты дословно из файла экрана, через ключи.** Бот — `t("раздел.ключ")` из `content/texts.yaml`,
  мини-апп — `texts.*` из `miniapp/src/texts.ts`. Ключи бери те, что в спеке. Текста в спеке нет —
  ключ со значением `TODO` и строка об этом в PR. Не сочиняй формулировки сам.
- **Дисклеймеры** (`disclaimer.profile`, `not_advice`, `mark`) — дословно и на тех экранах, где указано
  в `product.md`.
- **Форма в боте:** кнопка до 20 символов, не больше двух кнопок в ряду, сообщение до 4 строк
  (исключения D4, D21). На «вы», без восклицаний и эмодзи. Даты «28 октября», год — только если не текущий.
- **Налоговых дат, сумм и порогов в коде нет.** Только из `content/obligations.yaml`, `workdays.yaml`,
  `nds.yaml` и конфига. В тестах — фикстуры из `backend/tests/fixtures/`, не реальные файлы аналитика.
- **`Event` — это аналитика.** Сущности календаря — `Obligation*`, `UserObligation`, `Task`,
  `Notification`, DTO `CalendarItem`.
- **Статус (`done`/`overdue`/`today`/`upcoming`) считает бэкенд** в часовом поясе пользователя.
  Мини-апп его не пересчитывает.
- **Четыре состояния** — загрузка, пусто, ошибка, получилось — на каждом экране, формулировки из
  таблицы в `product.md`, отличия — в файле экрана. После ошибки пользователь продолжает без перезапуска.
- **Мини-апп — только компоненты `@maxhub/max-ui` 0.5.0**, перечисленные в `docs/spec/README.md`.
  Чего нет — сделано по D5–D8 (сетка, скелетон, тост, сегмент, подтверждение удаления, дата).
  Свои компоненты сверх этого не заводи, новые npm-пакеты — не ставь.
- **Аналитика.** События и их `props` — только из таблицы в `product.md`, в файле экрана сказано,
  какие он шлёт. Действие без события — задача не готова.
- **MAX API и MAX Bridge не выдумывать.** Источник правды — `docs/max-api-notes.md`
  и https://dev.max.ru/docs. Методы Telegram по аналогии **не переносить**. Нужного метода нет
  в документации — так и напиши в отчёте, не угадывай. Пометка **[сверить]** — структура
  не подтверждена на живых апдейтах.
- **Сеть не внутри транзакции.** Ответ пользователю — через `ctx.reply` (уходит после коммита).
  Внешние данные — в начале обработчика, до первой записи в БД. Планировщик не держит транзакцию
  во время запроса к MAX.
- **Идемпотентность.** MAX может прислать одно событие повторно; повторная отметка, повторная сборка
  календаря, повторный `/start` не плодят дублей.
- **Секреты** — только в `.env`. В CI стоит gitleaks по всей истории.
- **Моки помечены явно** — `is_mock`, «ТЕСТОВЫЕ ДАННЫЕ».
- **Новый обработчик бота → тест** в `backend/tests/` на фикстуре апдейта
  (`backend/tests/fixtures/updates/`).

## Шаг 5. Проверка

Запусти и **приложи вывод** — не пересказывай, а покажи:

```bash
make lint          # ruff по бэкенду
make test          # pytest + typecheck мини-аппа
```

Если трогал `miniapp/` — дополнительно:

```bash
cd miniapp
npm run lint          # eslint
npm test              # vitest
npm run build         # tsc -b && vite build
npm run format:check  # prettier
```

Известное состояние: `npm run lint` даёт **одну** ошибку `react-hooks/set-state-in-effect`
в `miniapp/src/App.tsx:36` — её убирает T11. Если у тебя не T11, эта ошибка не твоя; любая **другая** — твоя.

Пройди сценарий руками и опиши, что видел:
- бот — `make dev-api` + `make dev-bot` (long polling) и переписка с ботом в MAX;
- мини-апп — `make dev-miniapp`, http://localhost:5173 (вне MAX — тестовый пользователь);
  внутри MAX — только после деплоя на прод-сервер и когда адрес мини-аппа прописан в настройках бота.
  Ни деплоя, ни подписки вебхука агент сам не делает. Проверить в MAX не удалось — так и напиши.

Зелёные тесты — не доказательство того, что сценарий работает. Скопируй в PR список «Готово, когда»
из файлов своих экранов и отметь, что проверено и как.

## Шаг 6. PR

```bash
gh pr create --fill
```

В описании обязательно:
- `Closes #<НОМЕР>` — если задача закрыта целиком. Если частично, **не пиши `Closes`**,
  напиши «Часть #<НОМЕР>» и перечисли, что осталось.
- Отчёт из четырёх разделов: **сделано / не сделано / допущения / вопросы техлиду**.
- Список «Готово, когда» с отметками.
- Ключи со значением `TODO`, если есть.
- Вывод `make lint && make test`.

Коммиты — по-русски, в повелительном наклонении: «Добавить обработку /start». Одна задача — один PR.

## Когда остановиться и спросить, а не решать самому

- Нужна новая зависимость или изменение моделей БД.
- Нужно выйти за «Можно менять».
- Документация MAX не подтверждает метод или структуру, которые нужны для задачи.
- Спека противоречит сама себе, `AGENTS.md` или коду, и этого нет в `docs/spec/decisions.md`.
- Зависимость по плану ещё не слита.

Во всех этих случаях: опиши ситуацию и варианты, дай рекомендацию, жди решения.
Молча выбрать за человека — хуже, чем подождать.
