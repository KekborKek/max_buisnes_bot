# Журнал решений (ADR-lite)

Формат: дата — решение — почему — какие альтернативы отбросили.

- 16.09.2026 — Стек: Python/FastAPI + SQLite на бэкенде, React + MAX UI в мини-аппе, Docker Compose, Caddy для HTTPS. — Техлид пишет на Python; кейс рекомендует React для MAX UI; один сервер проще сдавать и воспроизводить. — Node.js-бэкенд (техлид слаб в JS), Postgres (лишний сервис для MVP).
- 16.09.2026 — Задачи в GitHub Issues + Projects, по одной на агента; общие файлы меняет только техлид. — Агенты читают задачи через gh; меньше конфликтов. — Trello/Notion.
- 16.09.2026 — Внешние данные только через адаптер Mock/Real. — Ядро продукта не должно зависеть от чужого API; моки явно помечаются по требованию кейса.
- 16.09.2026 — В мини-апп добавлены dev-зависимости: vitest 5.0.1 + jsdom 30.0.1 + @testing-library (react 16.3.3, jest-dom 7.0.1, user-event 14.6.7), eslint 10.10.0 + typescript-eslint 8.70.0 + eslint-plugin-react-hooks 7.1.1, prettier 3.9.7. Версии зафиксированы точно, как у остальных пакетов. — Без раннера тесты фронта писались статическим разбором исходника (`backend/tests/test_miniapp_primary_button.py` парсил `App.tsx` регулярками): такой тест проверяет форму кода, а не поведение, и ломается от любого переименования. Линтера не было вообще — `make lint` покрывал только бэкенд. Проверено: чистая `docker compose build` занимает 26 с при лимите кейса 5 минут, то есть на бюджет сборки это не влияет. — Отбросили: оставить всё как есть (регексные тесты не дают гарантий); jest (медленнее и требует отдельной трансформации TS, тогда как vitest переиспользует конфиг Vite).
- 27.09.2026 — Схема БД: лёгкая миграция при старте, без Alembic (#20). После `create_all` `init_db` сверяет колонки существующих таблиц с моделями: недостающую колонку, которую можно добавить безопасно (nullable, со скалярным или серверным default; не PK, не UNIQUE и не в уникальном индексе), добавляет `ALTER TABLE … ADD COLUMN` с `log.warning`, затем отдельным проходом создаёт индексы, в которые входят добавленные колонки (DDL в SQLite идёт в autocommit, ALTER не откатить); прочие расхождения (NOT NULL без default, лишняя колонка в базе, другая type affinity SQLite, NOT NULL в базе при nullable в модели) — только `log.error` с подсказкой, приложение стартует, данные не трогаются. Колонки автоматически не удаляются и не переименовываются. Правило для правок моделей: новые колонки — только nullable или с default; удалять и переименовывать колонки нельзя. Новый индекс на уже существующей колонке существующей таблицы автоматически не создаётся — только вручную. Типы сравниваются по affinity, а не по строке: база, созданная старыми версиями моделей (VARCHAR(20)→VARCHAR(32), DATETIME/TIMESTAMP), не даёт ложных тревог. Ключи `processed_updates` старше 24 ч удаляются при старте в `lifespan`. `make db-reset` — только для локальной базы и локального тома Docker, при `APP_ENV=prod` (окружение или `.env`) и при наличии тома `caddy-data` отказывается работать. — С 24.09 на проде живые пользователи; `create_all` не добавляет колонки в существующие таблицы, и без сверки новая колонка роняла бы запросы `no such column` молча, в фоне вебхука. — Отбросили: сносить базу на каждом деплое (теряются данные живых пользователей); Alembic (новая зависимость и отдельный шаг деплоя ради добавления колонок на хакатоне).
